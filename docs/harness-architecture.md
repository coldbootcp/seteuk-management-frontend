# 개인화 AI 하네스 구조

## 목표

이 프로토타입의 핵심은 “좋은 프롬프트 하나”가 아니라 학생마다 다른 근거를 가져오고, 도메인 규칙으로 계획하고, 결과를 검수하고, 반응을 다음 실행에 남기는 반복 가능한 실행 계층이다.

## 실행 흐름

```text
과제 입력
  ↓
Profile   학생의 진로·관심·강점·보완 역량을 작업용 프로필로 축약
  ↓
Plan      과제 조건과 학생에게 필요한 성장 방향을 탐구 계획으로 변환
  ↓
Retrieve  관련 활동과 도메인 지식을 필요한 만큼만 검색
  ↓
Generate  서로 다른 유형의 후보 탐구 3개와 개인화 근거 생성
  ↓
Review    과제 적합성·근거성·중복·난이도·안전성 검사
  ↓
피드백 저장 → 다음 추천의 개인화 신호
```

## 모델과 하네스의 경계

모델은 후보 문장과 구조화 결과를 생성한다. 하네스는 어떤 학생 정보를 가져올지, 어떤 도메인 규칙을 적용할지, 어떤 출력 형식을 요구할지, 무엇을 탈락시킬지, 어떤 피드백을 남길지를 결정한다. 따라서 Claude Code는 개발 도구로 쓸 수 있고 Claude 모델은 provider 후보가 될 수 있지만, 둘 다 제품의 하네스 자체는 아니다.

## 현재 데이터 단위

- `students`: 학생의 목표, 관심, 강점, 보완 역량
- `activities`: 교과 활동을 사건 단위 메모리로 구조화한 기록
- `recommendation_runs`: 입력과 출력, provider, 생성 시점의 실행 스냅샷
- `recommendation_feedback`: 추천별 저장·거절 신호

학생의 원문 전체를 매번 모델에 넣지 않고, 활동을 검색 가능한 사건 단위로 저장한다. 실제 서비스에서는 학교·사용자별 접근 통제, 보관 기간, 삭제 요청, 민감정보 마스킹을 별도 정책으로 구현해야 한다.

## 실제 모델 연결 시 인터페이스

```ts
type RecommendationProvider = {
  generate(input: {
    task: string;
    profile: StudentProfile;
    evidence: ActivityEvidence[];
    domainRules: DomainRule[];
  }): Promise<RecommendationCandidate[]>;
};
```

provider의 출력은 JSON Schema나 동등한 구조 검증을 통과해야 한다. reviewer는 최소한 다음을 확인한다.

- 학생 활동을 뒷받침하는 근거가 실제 검색 결과에 존재하는가
- 현재 교과와 과제 조건을 벗어나지 않는가
- 세 후보가 표현만 다른 사실상 동일한 주제가 아닌가
- 학생 수준에서 실행 가능한가
- 건강·입시·개인정보와 관련된 과도한 단정이 없는가

## 다음 기술 검증

1. 실제 모델 두 종류를 같은 평가셋에 연결해 provider 비교
2. 도메인 지식 검색 결과가 없을 때 답변을 보수적으로 제한
3. 30~50개 익명 학생 시나리오로 개인화 차별성·근거 정확성 측정
4. 저장·거절·수정 피드백을 선호도와 금지 조건으로 분리
5. 프롬프트·규칙·모델 버전별 실행 추적과 회귀 테스트 추가
